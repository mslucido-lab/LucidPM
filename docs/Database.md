# Database

## Server

SQL Server Express, local instance `localhost\SQLEXPRESS` — hardcoded as `SQL_SERVER` in `LucidPM/state.py`, not configurable via environment variable today.

## Databases

Two databases, both expected to exist on the same instance:

- `TenantCRM` — production (`PROD_DB_NAME` in `state.py`)
- `TenantCRM_Test` — test (`TEST_DB_NAME` in `state.py`)

The app toggles between them at runtime via `AppState.use_test_db`; nearly every query call site passes `db=` explicitly rather than relying on a single global connection.

## Connection

`get_conn(db)` in `state.py` connects via `pyodbc` using:

- **ODBC Driver 18 for SQL Server** (system-level install, not a pip package)
- Windows trusted connection (`Trusted_Connection=yes`)
- `Encrypt=yes`, `TrustServerCertificate=yes`

## Schema

`db/` at the repo root is the source of truth (reorganized 2026-08-17, moved out of the old `LucidPM/pages/TEST/` location):

- **`db/baseline_schema.sql`** — a complete, deterministic snapshot of the live schema (currently 43 tables, 51 FKs, 61 indexes), generated by `db/generate_baseline_schema.py`. This is how to stand up a clean database — run this against an empty database. It's a snapshot of *now*, not a replay of history; regenerate it (`python db/generate_baseline_schema.py`) any time the live schema changes rather than hand-editing it. Verified by actually running it against a throwaway scratch database and confirming table/FK/index counts matched the source exactly.
- **`db/history/`** — the pre-existing saved SQL scripts (Mark had been manually saving one per schema change), reorganized and cross-referenced against `dbo.SchemaChangeLog` — the database's own built-in change log, which turned out to be the real authoritative history (36 real changes recorded in Test, only 11 of which still have a runnable file; the rest are lost, log-entry-only). See `db/history/CHANGELOG.md` for the full timeline, what's missing, and a couple of things it turned up (a silently-applied-but-unlogged script, a logged-but-empty marker script, a harmless Test/Prod logging gap, and a confirmed-dead-code table naming collision already flagged in `lease_documents.py`'s own TODO comments).
- **`db/data_updates/`** — one-off **data** (not schema) migration scripts, named `YYYY-MM-DD_<description>.py`. Each is a Python script that connects via `LucidPM.state.get_conn`, guards its assumptions (e.g. "exactly one occurrence of the string being replaced"), prints a recovery copy of the pre-update values *before* writing, and only writes when passed `--commit` (dry run otherwise). Used when a handoff changes stored content rather than table structure — e.g. Handoff 52 swapping hardcoded clause numbers for `{{ClauseNumber}}` in `LeaseDocumentSections`.

`dbo.SchemaChangeLog` (`ScriptName`, `AppliedOn`, `AppliedBy`, `Notes`) is automatically populated for schema-object `CREATE`, `ALTER`, and `DROP` operations by the database-level `trg_LogSchemaChanges` trigger. It is installed on local and Azure `TenantCRM` and `TenantCRM_Test` (H70, 2026-09-12). New `db/history/` schema scripts must not add a manual `INSERT INTO SchemaChangeLog`; the trigger records the executed command as an `[AUTO]` row instead. Existing history scripts and their manual log rows remain historical records.

`db/generate_baseline_schema.py` currently emits tables, foreign keys, and indexes only. It does not emit database-scoped DDL triggers, so regenerating `db/baseline_schema.sql` does not include `trg_LogSchemaChanges`. Extending the generator is separate follow-up work.

### Multi-suite leases

`dbo.LeaseSuites` (H73) is the junction table for the suites covered by a lease.
It holds `LeaseID`, `SuiteID`, `IsPrimary`, and `RentAllocationPct`. `Leases.SuiteID`
remains the compatibility column and is synchronized to the one primary link. The
application validates that a linked lease has exactly one primary suite, positive
allocations totaling exactly 100%, and suites from only its own property.

## Secrets and encryption

The SMTP password and Anthropic API key are stored encrypted (Fernet) in `dbo.EmailConfig.PasswordEncrypted` and `dbo.AIConfig.APIKeyEncrypted`. The key(s) come from the **`LUCIDPM_FERNET_KEY`** environment variable (comma-separated — the first encrypts, all decrypt), not from the database. The app boots without it; only email/AI actions need it. See `.env.example` and `docs/DeveloperSetup.md` §5.

Because the key is now process-wide rather than per-database, a value written under one database decrypts fine against the other — the old `TenantCRM` vs `TenantCRM_Test` cross-key problem is gone. (Historically each DB auto-generated its own key into `AppSettings.LocalEncryptionKey`; Handoff 63's rotation runbook removes that row from both.)

Tenant SSN / DL use a separate Fernet key, `TENANTCRM_FERNET_KEY` (`pages/tally_import.py`).
